# Mingay

小規模事業者向けの在庫・販売管理アプリ。ダッシュボード、在庫管理（QRコード・値札印刷）、販売記録（手数料・広告費・送料込みの純利益計算）、仕入帳、経費帳、顧客管理をひとつのモバイル向けアプリにまとめています。

kokeshi-inventory と同じ思想（個人〜小規模事業主が一人でスマホから使う、Supabaseをバックエンドにした軽量アプリ）を踏襲しつつ、React + Vite 構成に刷新し、商材を特定ジャンルに固定しない汎用項目設計にしています。

## 機能

- **ダッシュボード**: 在庫数/売済数/売上/純利益のKPI、月別売上・利益グラフ、CSV出力
- **在庫管理**: 商品登録・写真・QRコード・値札印刷・検索/フィルタ、仕入日付・保存場所・ロット番号・状態(コンディション)・想定販売期限の管理、滞留期間（仕入日からの経過日数）の表示と滞留が長い順の並び替え
- **販売記録**: 販路（メルカリ/メルカリShops/BASE/ヤフオク/店舗など）・アカウント・取引ID・ステータスの記録、手数料/広告費の実額入力（未入力時は率から自動計算）、入金額・入金日の記録、顧客紐付け

### 販売記録の運用ルール

- 日付は**成約日（sold_at）**を入力する（入力日ではない）。突合も成約日ベースで行う
- **取引ごとに1行**を維持し、複数取引をまとめて1行に合算しない
- 販路内に複数アカウントがある場合（メルカリ・メルカリShops）は、新規入力時にアカウント名が必須。表記ゆれを防ぐため入力済みの候補がサジェストされる
- 手数料・広告費は**実額**の入力を推奨。実額を入れるとその値が使われ、未入力なら従来どおり率から計算する（既存データとの互換のため率の列も残している）
- 返品・キャンセルのステータスを付けた売上は、売上・利益・顧客の購入実績の集計から除外される
- 過去分でアカウントが特定できない行は `needs_review`（要確認）フラグで管理し、無理に全件特定しない
- **仕入帳**: 仕入先・仕入記録の管理、仕入れから在庫への追加
- **経費帳**: カテゴリ別経費、領収書写真、支払先・支払方法の記録、定期経費テンプレート（家賃などの毎月固定費を登録しておくと、計上日を過ぎた当月分をアプリ起動時に自動計上）

### 経費記録の削除

経費記録の**編集画面**に「この記録を削除する」を置いている。新規登録のときは出ない。押すと確認画面に切り替わり、日付・費目・メモ・金額を並べたうえで「⚠️ この操作は取り消せません」と出す。「やめる」で編集画面に戻る。

- 削除は取り消せない。`expenses` には削除履歴も `updated_at` もないため、消した記録は復元できない
- **自動計上された記録を削除しても、その月が計上し直されることはない**。計上済みの月はテンプレート側（`last_generated_month`）に記録されており、経費の行を消してもそこは変わらないため。確認画面でもその旨を出している。消した月の分を残したい場合は手入力で登録する
- 削除の失敗は保存と同じ扱いで、`saveWithRetry` を通すため一時的な通信の失敗は自動で再試行し、それでも失敗したら理由を画面に出して確認画面を閉じない

### 経費の費目

費目は `src/components/Expenses.jsx` の `CATS` が唯一の定義元で、経費入力フォームの選択肢・費目別の集計・定期経費テンプレートのフォームはすべてここから作られる。費目を増やすときは `CATS` に1行足すだけでよい。

| 内部値 | 表示 | 用途 |
|---|---|---|
| `rent` | 家賃 | 毎月発生する賃料 |
| `move_in` | 入居費用 | 入居時に**一回限り**かかる費用（ハウスクリーニング・鍵交換・仲介手数料など）。毎月の家賃と分けて集計したいので別費目にしている |
| `utilities` | 水道光熱費 | 水道代・ガス代・電気代など。家賃と同じ物件にかかるが毎月額が変わるので、定額の `rent` とは分けて集計する |
| `materials` | 梱包材料費 | 段ボール・緩衝材など。商品そのものの仕入は `purchases` 側 |
| `shipping` | 送料 | |
| `platform_fee` | 手数料 | 販売手数料など。`sales` の `platform` 列（販路区分）とは別物 |
| `equipment` | 備品 | |
| `other` | その他 | |

- DB側の `expenses.category` は制約のない `text` なので、費目を追加してもSQLの実行は不要
- 費目別の集計は金額が0の費目を表示しない。新しい費目は、最初の記録が入ってから一覧に出る
- 内部値を変えた場合は `LEGACY_CATEGORY_ALIASES`（旧内部値→新内部値）に追記する。コードのデプロイとデータ移行は同時に反映できないため、旧値のまま残っている行も正しく表示・集計できるようにしている

### 定期経費の計上日ルール

- 計上日は**1〜28日**で指定する（どの月にも存在する日のみ）
- 計上日が**土日・祝日にあたる月は、休み明けの最初の営業日に計上**する。金融機関の休業日を避けて引き落としが翌営業日になるため、実際の出金日に合わせる
  - 例: 27日が土曜 → 29日(月) / 27日が日曜 → 28日(月)
  - ゴールデンウィークのように休みが連続する場合も、営業日に当たるまで進める
  - 振替休日・国民の休日も休業日として扱う。春分の日・秋分の日のように年ごとに変わる祝日も正しく判定される
- **12/31〜1/3は対象外**。銀行の休業日ではあるが「国民の祝日」ではないため（元日のみ祝日）。計上日は1〜28日に制限されており、そこからずらしても年末年始には届かないため実害はない
- 28日指定で2月末が休業日にあたる場合など、ずらした結果が翌月になることがある。その月の分は翌月に入ってから計上されるが、「何月分か」の管理は元の月のままなので、月を飛ばしたり二重に計上したりはしない
- 同じ月の分が二重に計上されないよう、テンプレートごとに計上済みの月を記録している。アプリを何度開いても増えない

#### 「次回の計上予定」の表示

開始日・終了日・計上日の組み合わせによっては、**設定は保存できるのに一度も計上されない**状態を作れてしまう（例: 終了日を最初の計上日より前にしてしまう）。保存時にエラーが出ないため気づきにくいので、登録・編集フォームと一覧カードに次回の計上予定を表示している。

- 計上される場合: 「次回の計上予定: 2026-10-27」。計上日が土日・祝日でずれる場合は理由も添える
- 計上日を既に過ぎていて未計上の場合: 「次にアプリを開いたときに 2026-09-28 付けで計上されます」
- 一度も計上されない設定の場合: 「⚠️ この設定では計上されません（終了日が次の計上日より前です）」のように理由を出す

終了日の欄には、値が入っているときだけ「クリア」ボタンが出る。日付欄をタップしただけで今日の日付が入ってしまう端末があるため、意図せず入った終了日をすぐ戻せるようにしている。

#### 祝日データの更新手順

祝日の判定には [`@holiday-jp/holiday_jp`](https://github.com/holiday-jp/holiday_jp-js)（MIT）を使っています。祝日データはパッケージに同梱されているため、**法改正などで祝日が変わった場合はパッケージを更新してください**。

```
npm update @holiday-jp/holiday_jp
```

更新後は `npm run build` が通ることを確認し、変更をコミットしてデプロイしてください（`package-lock.json` の差分がデプロイに必要です）。

- 収録範囲は **1970年〜2050年**です。2050年以降の日付は祝日として判定されなくなり、土日のずらしのみが効きます
- 祝日が1日だけ移動するような単年の特例（過去にオリンピック開催に伴う移動がありました）も、パッケージの更新で反映されます
- **顧客管理**: 購入履歴・累計購入額

### 通信が一時的に失敗したときの挙動

読み書きは `src/lib/retry.js` を通していて、「もう一度投げれば通る」種類の失敗（`Failed to fetch`、502/503などのゲートウェイエラー、Postgresの接続系エラー）は自動で最大3回まで再試行します（1.2秒→2.4秒→4.8秒）。

- Supabaseの無料プランはアクセスがない期間が続くとプロジェクトが休止し、起床に数秒かかるため最初のリクエストが失敗する。再試行はこれを吸収する（有料プランでは休止は起きないが、モバイル回線の瞬断などには引き続き有効）
- 列が無い・制約違反・権限不足のような再試行しても直らないエラーは、待たせずにすぐエラーを返す
- 再試行しても失敗した場合は、**必ず理由を画面に表示し、フォームは閉じずに入力内容を残す**。無言で失敗して「入力できない」ように見える状態を作らない

## セットアップ

1. Supabase プロジェクトを作成し、`supabase/schema.sql` の内容をSQL Editorで実行する
   - 既存プロジェクトに対して仕入管理項目（仕入日付・保存場所・ロット番号・状態・想定販売期限）を追加する場合は、`supabase/schema.sql` 末尾の `alter table items add column if not exists ...` を SQL Editor で実行してください（anon keyからは実行できないため、Supabase の SQL Editor で手動実行が必要です）
   - 既存プロジェクトに定期経費機能を追加する場合は、`supabase/schema.sql` の `create table if not exists recurring_expenses (...)` と、その直後の `alter table expenses add column if not exists ...` 3行を SQL Editor で実行してください
   - 既存プロジェクトに売上の多販路・複数アカウント対応を追加する場合は、`supabase/schema.sql` の `alter table sales add column if not exists ...` 9行と、その直後の初期化用 `update` 2行を SQL Editor で実行してください
   - テーブルを追加したのにアプリから常に0件に見える・保存できない場合はRLSを確認してください。ダッシュボードの Table Editor からテーブルを作るとRLSが既定で有効になり、ポリシーが無いと anon key からは全件拒否になります。確認・修正のSQLは `supabase/schema.sql` 末尾のコメントにあります
2. Storage に `mingay-photos` という名前の公開バケットを作成する
3. `.env.example` を `.env` にコピーし、Supabaseの URL と anon key を設定する

   ```
   VITE_SUPABASE_URL=https://your-project.supabase.co
   VITE_SUPABASE_ANON_KEY=your-anon-key
   ```

4. 依存関係をインストールして起動

   ```
   npm install
   npm run dev
   ```

## デプロイ

Vercel等の静的ホスティングに `npm run build` の出力（`dist/`）をデプロイしてください。環境変数（`VITE_SUPABASE_URL` / `VITE_SUPABASE_ANON_KEY`）をホスティング先にも設定する必要があります。

> 個人利用を想定し、認証なし・Supabase anon keyをフロントエンドに含める構成です。複数人で使う、または公開環境に置く場合はSupabaseのRow Level Securityと認証の追加を検討してください。
